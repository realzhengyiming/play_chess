# 空间棋卧室升级版：思路精髓与实施方案（V2）

> 版本：V2.0  
> 日期：2026-08-10  
> 当前范围：先完成卧室，验证成功后再扩展客厅。

## 一句话定义

空间棋真正需要的不是“让每件家具拥有越来越多的采样走法”，而是：

> 像棋手一样先识别房间局型，匹配少量棋谱，再下完整的模块棋，最后展开成独立家具并通过现有几何与通行验收。

现有系统最值得保留的是多边形、碰撞、门窗、功能区、Bitset、通行和质量诊断；最需要调整的是搜索动作的抽象层级。

## 一、为什么先做卧室

卧室是验证“棋谱 + 模块棋”最合适的第一阶段：

- 核心锚点明确，床通常决定主要空间关系；
- 睡眠组、收纳组、工作组和休闲组具有较强模块性；
- 家具数量和关系比客餐厅更可控；
- 矩形、狭长和大套间已经能覆盖三类代表性局型；
- 当前目录已有大量卧室参考图、生成截图和真实识别房型。

卧室跑通后，客厅可以沿用同一框架，把模块替换为会客组、视听组、餐组和收纳组。

## 二、新旧版本边界

旧版 `bedroom-space-chess-V3.html` 保持不动，继续作为现有单件家具 Beam 搜索基线。

新版 `bedroom-space-chess-V3_upgrade.html` 独立开发，第一版只处理卧室，验证：

1. 房间局型能否稳定识别；
2. 棋谱能否把搜索动作限制到少量高价值分支；
3. 模块内部能否一次保持完整家具关系；
4. 搜索节点和耗时能否显著下降；
5. 每个方案能否解释使用了哪条棋谱、下了哪些模块棋。

新版不修改旧版页面、旧版脚本和旧版配置，避免实验影响当前可用版本。

## 三、已有样例如何使用

### 1. 七张设计参考图

根目录的 `img_v3_*.jpg` 用于提炼关系和构图，不直接复制坐标：

- 外围墙面承担稳定功能；
- 中部家具必须形成完整关系组；
- 剩余留白必须能解释为通路或活动面；
- 大空间优先增加完整模块和升级家具模数。

### 2. 当前生成截图

`docs/layout-v13`、`screenshots/review-v*` 和 `artifacts/qa-screenshots` 用于人工挑选“金牌局面”。每个候选应标记为：

- `accepted`：可作为正向棋谱；
- `acceptable`：硬规则正确但设计一般；
- `rejected`：不能学习，并记录失败原因。

截图本身不够，最终认可的方案还必须保存房间、门窗、家具坐标、模数、模块关系和设计说明。

### 3. `space_chess_results.json`

其中已有家具位置、模数、墙索引、相对关系和评分，可以作为“布局快照格式”的起点，但旧结果较简单，不直接作为丰富卧室的最佳真值。

### 4. `samples/*.json`

这些是真实户型轮廓与门窗输入，用于验证棋谱泛化，不作为好布局标签。

### 5. `module-growth-prototype.html`

这是现成的模块棋实验雏形，已经验证睡眠、收纳、工作、休闲等模块可以整体生成。但它仍是硬编码、固定门窗和 0.1m 扫描，只能借鉴模块数据结构，不能直接并入正式引擎。

## 四、卧室第一版局型

第一版只建立三类卧室棋谱。

### 棋谱 A：标准外围型

适用：近矩形、面积约 9–18㎡、长宽比不高。

顺序：

1. 睡眠组占据完整主墙；
2. 收纳组占据相邻或对侧完整墙；
3. 工作组优先靠采光墙；
4. 中央保持连续活动面。

### 棋谱 B：狭长酒店型

适用：长宽比较高、面积约 14㎡以上。

顺序：

1. 睡眠组建立主轴；
2. 床尾媒体组与床形成面对关系；
3. 收纳组使用长侧墙；
4. 工作组或小休闲组占据剩余完整墙段；
5. 保留贯穿入口与床侧的纵向通路。

### 棋谱 C：大卧室套间型

适用：面积约 18㎡以上且具有足够连续墙面。

顺序：

1. 睡眠组；
2. 收纳组；
3. 工作组；
4. 正式休闲组；
5. 必要时加入梳妆或媒体模块；
6. 模块之间保持组团完整和中心连通。

## 五、搜索动作

家具继续作为独立物理对象，但搜索不再始终一件一手。

```text
物理层：床、床头柜、衣柜、桌、椅分别碰撞和输出。
搜索层：睡眠组、收纳组、工作组、媒体组、休闲组作为模块棋。
```

以睡眠组为例，一手棋同时决定：

- 主墙；
- 床的 S/M/L 模数；
- 左、右或双床头柜；
- 靠墙起点、中心或终点；
- 是否具有床尾凳；
- 床侧和床尾使用区。

模块展开后，所有家具仍必须逐件通过越界、碰撞、挡门和使用区检查。

## 六、候选点原则

升级版不通过缩小采样步长提高质量，只生成具有设计意义的临界位置：

- 墙段起点；
- 墙段中心；
- 墙段终点；
- 门窗净距边界；
- 与已落模块边缘对齐；
- 满足最小通行净距的相切位置。

一段墙通常只产生少量模块动作。家具模数在模块内部选择，不再与全房间所有均匀坐标形成乘积。

## 七、分层搜索流程

```text
房间特征
  ↓
局型识别
  ↓
选出 1–3 条候选棋谱
  ↓
按棋谱顺序搜索模块棋
  ↓
模块展开成独立家具
  ↓
硬规则和通行验收
  ↓
多目标排序并输出 3 个方案
```

第一版建议 Beam 宽度为 16；每个模块在每个父局面只保留少量语义候选。

## 八、局部控制方式

模块棋使局部关系在模块内部闭合：

- 双床头柜对称只属于睡眠组；
- 工作椅贴书桌只属于工作组；
- 电视柜的本体属于媒体组，它可以在床与卧室沙发之间选择更合理的观看目标；
- 小沙发与茶几的围合只属于休闲组。

全局搜索只关心模块占地、墙面需求、通行影响、模块完整度和模块间关系。以后用户锁定某件家具时，可根据模块依赖图只重新生成该模块和邻接模块，不必重搜整个房间。

## 九、验收指标

第一版卧室升级页的目标：

- 旧版页面和脚本零修改；
- 页面能够解释识别出的局型和选中的棋谱；
- 每一步搜索显示的是完整模块，而不是孤立家具；
- 睡眠、工作等强关系家具不会被后续 Beam 意外拆散；
- 默认矩形卧室 Beam 宽度不超过 16；
- 常规房间节点数控制在数百级，而不是数万级；
- 常规矩形卧室目标计算时间低于 100ms；
- 后续接入主引擎时，最终方案必须继续通过 0.50m 通路、零孤岛和门窗使用区验收。

## 十、演进顺序

1. 完成独立卧室升级页的矩形模块搜索；
2. 将认可样例整理为结构化金牌局面；
3. 用金牌局面校正三条卧室棋谱；
4. 接入真实识别轮廓和门窗；
5. 复用旧引擎精确通行与质量验收；
6. 建立局部锁定和局部重排；
7. 卧室验收通过后，以相同架构实现客厅模块。

## 十一、V2.1 异形拓扑闭环进展

当前升级分支已经不再把识别卧室压成 `width × depth` 外接矩形，而是建立了独立的房间拓扑层：

1. 保留识别 JSON 中的全部正交多边形角点；
2. 将轮廓逐边编译为带方向和室内法向的墙段；
3. 把真实门窗投影到对应墙段的局部区间；
4. 模块用“墙段索引 + 沿墙距离 + 向室内展开”落子；
5. 家具本体和模块使用区均逐件通过真实多边形包含检查；
6. 通行栅格只在真实轮廓内部建立，并从真实入口开始连通；
7. 当前拓扑、门窗、棋谱与方案自动保存到浏览器本地，也可导出完整 JSON。

目前支持矩形、L 形、缺角和带凹位的正交卧室。斜墙仍明确拒绝，避免把不受支持的几何悄悄近似成矩形。

## 十二、V2.2 可替代的模块软关系

模块间关系现在存在棋谱中，但不作为“不正对就禁止”的硬规则。狭长卧室的第一条关系是：

- 主体：媒体组；
- 可选目标：睡眠组或休闲组；
- 选择方式：对所有合法目标评分，取最高满足度，不预先硬绑床；
- 评分维度：中心线偏移、双方朝向、墙面对向、观看距离与视线遮挡；媒体正面与床尾/沙发正面必须同时看向对方，任一端垂直时关系不成立；
- 容错方式：完全正对得分最高，偏移越大分数越低，但轻微偏移仍是合法走法；
- 搜索用法：关系先派生少量 `0 / ±0.35m / ±0.70m` 语义候选，再同时进入局部落子分和最终全局分。

关系分只帮助“同一功能模块放在哪里”，不应压过“是否还能多摆一个正式功能模块”。为防止 Beam 只留下一群高分但同质的棋局，当前会为不同“功能—墙段—位置”组合保留代表分支，然后再用局部分填满 Beam 16。

## 十三、V2.3 使用场景的“是 / 否 / 条件”关系

生活语义不适合只用布尔开关表达，当前分为三类：

1. **正向关系**：例如媒体组与床尾的双向正对，越满足越加分；
2. **负向关系**：例如工作组回避电视观看轴，冲突越强越扣分，但狭小房间仍可保留变通；
3. **条件替代**：媒体组优先服务床，只有休闲组确实形成观看座位时才作为降级目标，两者不再等价。

模块内部也采用同样逻辑。单人床先作为核心家具落子，主棋完成后再尝试升级为“单人床＋双床头柜”。若第二个床头柜会与门、家具或使用区冲突，才退回单床头柜变例。

对高柜和定制柜，除了检查柜体是否放得下，还会计算柜前使用区封堵相邻空墙的长度。这个“墙面机会成本”同时进入局部落子分和最终全局分，避免角落小高柜为了填空，反而浪费一整段可用墙面。

## 十四、V2.4 隐私规范、微秒计时与压缩棋谱树

“床不宜正对门”已作为棋谱中的环境负关系，而不是写死在几何内核中。隐私冲突由四部分连续计算：

1. 床尾方向指向门口的程度；
2. 床中轴与门口轴线的重合度；
3. 床与门口的距离；
4. 门口到床的视线是否通透。

完全正对仍然是合法候选，只是隐私满足度更低。在 4×5m 对照测试中，直对门的隐私分约为 28%，错开门轴后约为 86%，两者都不会被硬性删除。

搜索内核现在为每个模块回合、睡眠附件补全、定制柜残局和终局验收记录微秒耗时，同时保留总毫秒耗时。页面不渲染数千个原始节点，而是渲染压缩 Beam 棋谱树：

```text
空房间
  └─ 睡眠组：候选 N → 保留 16 → 本方案选中某墙段
       └─ 附件补全：补第二床头柜 / 保留退化变例
            └─ 收纳组……
                 └─ 定制柜残局……
                      └─ Top 3 终局验收
```

这种展示只读取搜索已有的统计数据，不会扩大 Beam 或新增几何候选。

## 十五、V2.5 L 形凹角柜的朝向规则

L 形凹角中经常同时存在一段很短的横墙和一段较长的竖墙。如果柜体只因为“能塞进短墙”就背靠短横墙，柜门会朝向长墙的家具布置带，使用区还会锁死整段空墙。

当前规则是：

1. 检测柜体是否位于真实多边形的凹角端点；
2. 若当前依附墙是短墙，而相邻垂直墙明显更长，该朝向直接从候选集移除；
3. 高柜、薄柜和成品衣柜使用同一规则，不再只约束 `tall=true` 的高柜；
4. 对演示异形卧室，柜体应改为背靠左侧竖墙，柜门法向向右，即朝房间开阔区开启。

该页面的 CSS 和 JavaScript 资源同时带有 V2.5 版本号，用于避免浏览器继续执行旧的角落高柜和单床头柜逻辑。

下一阶段按以下顺序继续：

1. 把旧引擎更严格的 0.50m 通路和零孤岛验收接入拓扑层；
2. 已完成第一版定制柜残局模块：从主模块落子后的剩余连续墙段动态生成高柜或薄柜，允许重复落子，并继续接受门窗、使用区和通行验收；
3. 在页面展示每个模块的合法候选数、硬拒绝原因、局部分和全局分变化；
4. 用人工认可的金牌布局校正棋谱关系权重；
5. 增加局部锁定与只重排邻接模块的能力。

## 最终原则

> 棋谱不是某个房间的绝对坐标，而是一组适用条件、模块顺序、墙面角色、对象关系和可降级变例。

> 模块不是不可拆的组合家具，而是一手完整空间决策；落子后仍展开成独立家具接受全局几何验收。

> 速度不来自更快地枚举更多点，而来自从一开始就只生成少量有意义的走法。
