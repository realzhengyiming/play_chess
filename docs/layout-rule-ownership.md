# 空间棋规则归属

目标不是“把代码全部搬进 JSON”，而是保证同一种设计语义只有一个真相源。

## 必须留在引擎代码

- 多边形、旋转矩形、精确碰撞与 Bitset broad phase；
- 门窗几何、功能区几何和水漫可达性计算；
- 候选生成器、Beam 状态扩展、去重、增量缓存；
- 读取配置、执行通用公式和输出诊断信息。

这些是计算能力，不是卧室或客厅的设计偏好。

## 必须进入全局配置

- 家具类型、尺寸模数、数量范围、优先级；
- 家具间的相对位置、距离、朝向和使用区；
- 面积档位、完整功能组、丰富度目标；
- 地面、墙面、通行、关系等评分权重和质量门槛；
- 候选预算、Beam 宽度、库存尝试次数和剪枝启用阶段；
- 末轮填缝柜的尺寸、预算、验收门槛。

## 允许留在代码的安全不变量

- 配置必须通过契约校验后才可保存或运行；
- 实体不得越界、挡门或相互穿透；
- 最终输出必须满足零孤岛；
- 产品当前要求的硬通路不得低于 0.50m。

安全不变量可以拒绝危险配置，但不能偷偷给缺失配置补一套设计参数。

## 禁止做法

- 按家具 ID 在引擎里写面积阈值、奖励数字或场景特判；
- 配置中心加载后静默改写用户规则；
- 搜索期、最终评分和末轮补齐各自维护一套同名阈值；
- 回归测试只读取 default，却声称验证了当前运行效果；
- 用“家具件数更多”替代功能模块完整、墙地连续和真实可用性。

## 迁移原则

一次只迁移一个规则族，并保持基线布局、质量分解和性能数据可对比。迁移前先记录旧规则的输入、输出和调用阶段；迁移后删除旧代码，不允许长期双轨。
